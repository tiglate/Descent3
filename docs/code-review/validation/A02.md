# A02: coverage extension (Linux Debug batch 1)

## What ran

clang-tidy 18.1.3 ran with the baseline check set over **every first-party
translation unit** in the Linux Debug compilation database: 387 of 387 sources,
excluding `third_party/` and generated build files. This is up from 16 in the
original sample. Every invocation exited 0; none failed or timed out. Headers
under the repository root were included and deduplicated by location.

The machine-readable record is [a02-linux-debug.json](../a02-linux-debug.json).
It holds per-module translation-unit counts, failures, diagnostic counts per
check family, and every analyzer finding, each flagged with whether it appeared
in the original sample. The raw logs are in the ignored `build/code-review/a02/`.

## Batch 3: network string helpers and portal indexes (2026-11-10)

### Network strings

`MultiGetString` copied up to the 255 bytes announced by the packet's length
byte into the caller's buffer, and relied on the sender for a terminator. Six
call sites write into `msafe_struct::name[32]` (`multisafe_server.cpp`) and one
into `DMFC_team_names[team][16]` (`dmfcpackets.cpp`). A peer sending a longer
string overflowed those fields, and no destination was guaranteed to be
terminated.

`MultiGetString` now takes the destination size, and an array-reference
template supplies it at every call site. The compiler accepted all 21 existing
calls unchanged, so each one passes a real array. The copy is clamped and
always terminated, and the read position still advances by the full encoded
length, so following fields stay aligned.

`MultiAddString` truncates strings over 254 characters instead of writing a
wrapped length byte (the old check was a debug-only `assert`). The packet
format is unchanged. The helpers are inline in `multi_external.h`, so loadable
modules get the fix when rebuilt, and the module ABI is unchanged.

`multi_string_tests` (Linux) covers four cases:

- round trip and field alignment
- a 200-byte unterminated string into a 32-byte field (truncated, terminated,
  and the next field still read correctly)
- empty and exact-fit strings
- clamping of over-long outgoing strings, which runs in Release because Debug
  keeps the `assert`

Not covered: the `MultiGet*` readers in general still trust that a packet
holds the fields they read. Bounding reads to the received packet length
needs the packet size plumbed through every handler, and is a separate
multiplayer hardening task.

### BOA portal indexes

`BOA_DetermineStartRoomPortal` can return -1. These uses now treat that as "no
connecting portal", matching the neighboring checks:

- `hlsoundlib.cpp`: two distance branches add no portal distance or cost.
- `aipath.cpp`: the external-room branch skips the neighbor.

### Verification

- Debug and Release builds pass; CTest passes 234 of 234 in both
  configurations (one opt-in real-GL test skipped).
- The gate reports 35 findings, zero new.
- A rescan of the touched files shows only the previously triaged `aipath.cpp:86`
  ownership false positive.

## Batch 4a: special-packet size (2026-11-10)

`MultiDoSpecialPacket` copied a network-supplied `size` into a
`MAX_GAME_DATA_SIZE` stack buffer, guarded only by a debug assert. Clients
handle `MP_SPECIAL_PACKET` from the server, and the server handles the same
packet type from any connected client (`MultiClientSendSpecialPacket`), so a
negative or oversized `size` overflowed the stack on either side.

The handler now receives the sub-packet length validated by
`MultiProcessBigData`. It rejects a size that is negative, larger than the
buffer, or larger than the rest of the sub-packet, and zero-fills the buffer
handed to the game module. Both senders refuse a payload that does not fit.
Verified by source review, Debug and Release builds, and CTest 234 of 234 in
both configurations. No multiplayer session was run.

## Batch 4b: multiplayer packet hardening (2026-11-11)

Packet handlers receive only a data pointer and trust every field. This batch
bounds the dangerous sinks: copy lengths, array indexes, and messages a role
should never accept.

### Defects found and fixed

| Area | Direction | Defect | Fix |
| --- | --- | --- | --- |
| `networking.cpp` `nw_psnet_buffer_packet` | Anyone to anyone (unauthenticated UDP) | Datagrams are read into a 1500-byte buffer but copied into a 512-byte slot without a length check. **Any UDP packet over 512 bytes sent to the game port overflowed static memory.** Found by fuzzing; glibc reported `*** buffer overflow detected ***` and aborted. | Drop datagrams larger than `MAX_PACKET_SIZE`. |
| `networking.cpp` `nw_WorkReliable` | Peer with a reliable socket | Signed `data_len` was never checked against the bytes received; a negative value became a huge copy. | Reject a `data_len` that is negative, larger than the received payload, or larger than the buffer. |
| `MultiProcessData` | Anyone to server | A server dispatched server-to-client messages from any address. `MP_CONNECTION_ACCEPTED` from an unknown sender overwrote `Netgame.mission`/`name`/`scriptname` with unbounded `memcpy` and called `LoadMission` (forced mission reset, memory corruption). 51 message types had no accept condition at all. | A server ignores the 60 message types only servers send (derived from the send sites), from any sender. |
| `MultiDoMyInfo`, `MultiDoPlayer`, `MultiDoPlayerEnteredGame`, `MultiDoReadyForLevel` (server and client) | Client to server, and server to client | Ship name (`PAGENAME_LEN` stack buffer), tracker id and guidebot name (32 bytes, debug-only assert) were copied with packet lengths up to 255; slots were unchecked. `slot > MAX_PLAYERS` was off by one. | `MultiGetString` (bounded, terminated); slot checks; `>=`. |

| 57 handlers in `multi.cpp` | Both | 92 packet-supplied indexes into `Players`, `NetPlayers`, `Objects`, `Server_object_list` (1500 entries, indexed by a 16-bit value, including a **write** in `MultiDoObject`), `Rooms`, room portals, weapon batteries and spew slots. | `MultiValidSlot/Objnum/Room/WB/Spew` right after each read; existing sentinels (65535, -1, 255) are kept. `MultiServerToLocal` maps 9 inline lookups. ### Review follow-up: legitimate traffic and further sinks

A second pass checked that the new checks do not drop valid packets, and
covered sinks the index scan cannot see:

- **Sentinels written by senders:** every sender that writes a sentinel
  (65535 parent or child object, 255 lifeleft, -1 object numbers) was matched
  against the inserted checks, and each sentinel is accepted.
- **Fields used in only one branch:**
  - Restart start positions (`MultiDoObserverChange`), `start_index`
    (`MultiDoPlayer`/`MultiDoPlayerEnteredGame`) and `start_slot` are
    legitimately negative for auto-waypoints. The checks now reject only values
    of `MAX_PLAYERS` or more. The observer position fix no longer indexes
    `Players` with a negative value, which was an original out-of-bounds read.
  - Join-object room checks skip doors, which carry no room number. A
    compiler `-Wmaybe-uninitialized` warning exposed this.
- **Marker message rows:** `MarkerMessages[id]` is bounded inside the marker
  branch only. An out-of-range id is read into a discard buffer.
- **Stored object numbers:** small-view object numbers that any connected
  client sends (`MultiDoWeaponsLoad`) were later used to index `Objects` every
  frame on the server. They are now range-checked when received.
- **Room and face arguments:** decoded room numbers passed to
  `ObjCreate`/`ObjSetPos` in six handlers plus `MultiDoAdjustPosition`, and
  face numbers passed to `BreakGlassFace`/`ChangeRoomFaceTexture`, are
  validated. `MultiDoPlayerPos` already validated its rooms.

### Evidence

- **Fuzzing (Linux, Release dedicated server, Retribution level 1, Anarchy, UDP port 2999):**
  - Before the fixes: the original code crashed within seconds (the over-512-byte copy), and a forged `MP_CONNECTION_ACCEPTED` reset the server's mission.
  - After the fixes: every message type 1–255 was sent 300 times with random payloads from an unknown sender, then five 40-second mixed runs followed (about 1.5 million datagrams with honest, short, lying and truncated lengths, routed to the reliable, unreliable and other layers). No crash, no level reset, and the server stayed up.
  - Debug builds trap on malformed packets via `Int3()` by design, so fuzzing used Release.
- Debug and Release builds pass; CTest passes 234 of 234 in both configurations; the gate reports 35 findings, zero new.

### Not verified, and known remaining risk

- **Fuzzing scope:** the fuzzer is an unknown sender. On a server, handlers
  behind `ACCEPT_CONDITION(NETSEQ_...)` reject it, so the connected-player
  handlers (my-info, request-to-fire, chat, position and so on) were reviewed
  in source only and never executed with hostile input.
- **Other function-argument sinks:** object type and id given to `ObjCreate`,
  and sound, texture and weapon ids passed into engine functions, were not
  audited.

- **No real multiplayer session:** a LAN game (join, play, chat, file transfer, observer mode, level change) and a NAT'd client have not been tested. A user check is needed before release.
- **Client-to-server spoofing:** the protocol still trusts the player slot written inside client packets instead of the sender's matched slot, so a client can act for another slot. Fixing that changes protocol behavior and needs LAN and NAT testing.
- **No client-side fuzzing:** clients need the interactive join screen.
- **DMFC modules:** game-mode packets other than the player records were reviewed only by the index scan.
