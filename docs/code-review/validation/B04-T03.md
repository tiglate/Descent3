# B04 / T03 — renderer failure handling and analyzer disposition

**B04: Review**, with Linux implementation and validation complete; Windows
compilation/runtime and interactive game/settings transitions remain pending.
**T03: Done** for disposition of the original Linux analyzer candidates. This
does not close B04's remaining platform and gameplay acceptance gates.

## Behavior

Failed renderer startup or reinitialization now returns failure after cleanup.
The preference setter propagates that result before applying gamma to a renderer
that no longer exists. Engine callers in screen-mode changes, settings, TelCom,
editor initialization and debugger resume stop on failure. A renderer failure
cannot continue the game loop through Debug's Ignore/Cancel path. Successful
initialization, graphics quality defaults and user font/control preferences are
unchanged; no serialized formats or commercial assets were modified.

| Area | Change |
| --- | --- |
| Readiness | Both renderer flags are published only after setup, shaders, texture caches, upload tables and defaults succeed; cleanup clears them |
| Partial setup | One failure boundary catches setup/shader/allocation exceptions, preserves a bounded diagnostic and cleans up |
| GL entry points | Reloaded for every context; registration metadata survives both successful and failed loads |
| Context lifetime | Cleanup deletes GPU resources while its context is current, then clears entry points and destroys the context |
| Lost context | When it cannot activate the context, cleanup skips GL deletions, releases CPU owners, and destroys the context to reclaim GPU resources |
| Framebuffers | Explicitly releases the framebuffer and its renderbuffers before context destruction |
| Library lifetime | Uses SDL's loader/unloader as a matched pair, preserving the loaded library during a successful resize and releasing it on full close/failure |
| CPU allocations | Checks all four cache and three upload/table allocations; partial owners are freed and reset |
| Error messages | Truncates long driver diagnostics safely and treats error text as data when reporting a fatal renderer failure |
| Retry | A subsequent explicit initialization can load entry points, create resources and draw again after failure or full shutdown |

The SDL3 return-value corrections follow the documented boolean contracts for
[SDL_Init](https://wiki.libsdl.org/SDL3/SDL_Init) and
[SDL_GL_LoadLibrary](https://wiki.libsdl.org/SDL3/SDL_GL_LoadLibrary). Loading
entry points again follows SDL's
[context lifetime guidance](https://wiki.libsdl.org/SDL3/SDL_GL_GetProcAddress).
Context activation checks the result of
[SDL_GL_MakeCurrent](https://wiki.libsdl.org/SDL3/SDL_GL_MakeCurrent).
The installed SDL3 headers were also checked.

[Lifecycle tests](../../../renderer/tests/lifecycle_tests.cpp) compile the
production renderer entry points and shader/resource classes. Linux linker
wrappers inject video, library, attribute, window, context, activation,
entry-point lookup, drawable-size, framebuffer, shader creation/compilation,
program-link and uniform failures. Reinitialization cases change both dimensions
and gamma. Each failure is followed by ownership checks and a successful retry
that uses renderer setters and draws through the production vertex-buffer path.

The allocation case checks all seven allocation positions for both packed and
unpacked uploads at startup and reinitialization: 28 injected failure scenarios
inside that case. It verifies that the selected fault was consumed, partially
allocated CPU buffers were released, and retry succeeds. Additional cases cover
repeated shutdown, a context that cannot be made current during shutdown,
invalid dimensions/selection, long diagnostics containing percent characters,
and an Error handler that returns. GPU IDs and live windows/contexts/library
references are tracked; context destruction reclaims remaining GPU IDs.

Synthetic bitmap, input and application data keep these tests independent of
game assets. GL stubs use signatures from the production GL entry-point list.
The real-driver case forwards the SDL calls to SDL, uses actual GL entry points
and shaders, and checks nonblack RGB output rather than accepting the alpha
channel as proof of drawing. It supplies a simple orthographic transform and a
synthetic bitmap. This is a renderer smoke test, not an interactive game session
or a hardware-driver compatibility matrix.

Fault injection requires Linux's GNU-style linker wrapping and
`ENABLE_MEM_RTL`. Test discovery uses `PRE_TEST` to keep Debug and Release
executable registrations separate in multi-configuration builds. ASan/UBSan
instrument the renderer and local dependencies in the existing sanitizer build;
prebuilt SDL/GTest are not instrumented. LeakSanitizer ran outside the sandbox
for its process scan. Original-source comparisons used isolated objects and
original renderer headers, without replacing the working engine objects. The
comparison supplies only the newly added fatal-reporting API symbol to link the
fixture; the selected baseline cases do not call it.

Full-suite verification also sets `CMAKE_GTEST_DISCOVER_TESTS_DISCOVERY_MODE`
to `PRE_TEST` in the local build cache and checks CTest's executable paths.
Existing targets used shared post-build discovery files, which could select
the most recently linked configuration despite `ctest -C Debug`. Earlier
checkpoint suite totals recorded the requested CTest configuration without this
path audit; they are not proof that every case used a Debug executable. B04's
final full-suite result uses verified Debug paths. Extending the discovery
policy to the general CI/developer workflow is recorded under A01.

## Analyzer disposition and remaining gates

The original registry and WAV candidates were removed and validated by M04 and
M02/M03. M06 fixed and reproduced the CFILE candidate: Error can return in Debug,
so its null-dereference diagnostic represented a real failure path.

The remaining optional diagnostics arise because clang-tidy analyzes individual
entry points without the caller's successful initialization path. The rendering
API requires successful initialization and main-thread use before draw/state
operations. Successful setup constructs gRenderer before defaults use it; both
readiness flags are set only after initialization finishes. Shutdown clears
readiness and destroys it. Reinitialization failure now propagates before gamma,
and all active engine callers of the preference/init APIs check failure before
continuing rendering. Normal operation, failure, cleanup and retry have focused
runtime evidence, including real GL drawing. No optional-access suppression or
blanket no-op guard was added to drawing functions. Calling drawing APIs before
initialization or after shutdown remains outside their contract.

This resolves T03's original Linux triage. B04 remains Review because its
acceptance includes Windows context-specific behavior and interactive settings,
screen-mode and debugger transitions. An offscreen Linux driver cannot establish
those results. No claim of complete platform coverage is made.
