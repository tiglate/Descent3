## CFILE finding and repair

The baseline `clang-analyzer-core.NullDereference` warning was not a false
positive. [Error()](../../../ddebug/error.cpp) can return in `_DEBUG` when the
user selects Ignore or Cancel, or resumes after Retry. Marking it `noreturn`
would misrepresent that contract.

All three CFILE opening paths allocated a handle, called Error on failure, and
then dereferenced the null pointer. Disk opening also continued after a failed
filename duplication, returning a handle with a null name. Each path had already
acquired a FILE stream; returning without releasing it would leak a descriptor.

The fixed [implementation](../../../cfile/cfile.cpp) closes its acquired stream
before reporting failure and returns null if Error returns. A failed filename
duplication also frees the allocated CFILE. For HOG entries, this applies both
to a stream taken from the library cache and to a newly opened stream. A retry
reopens the archive; another active member stream remains usable. Successful
opening, shared library-entry names, public signatures and binary formats are
unchanged. Release retains its existing fatal Error behavior, with cleanup now
performed before the handler runs.

[Allocation regressions](../../../cfile/tests/allocation_failure_tests.cpp)
link the production CFILE library. Linux linker wrappers inject handle/filename
allocation failures, count open streams and live handles, and replace Error with
a returning handler. They assert that the fault was actually injected, cleanup
completed before returning, and retry preserves contents. The seventh case checks
normal handle lifetime. HOG fixtures are generated from redistributable synthetic
bytes, with no commercial assets or user preferences involved.

The test target is enabled for Linux with `ENABLE_MEM_RTL`, because its wrappers
target that allocator configuration and GNU linker symbol wrapping. Other
platforms do not run these injected tests. The Error wrapper exercises the
returning control-flow contract rather than an interactive debugger dialog.

## Remaining renderer triage

The normal initialization path in
[HardwareOpenGL.cpp](../../../renderer/HardwareOpenGL.cpp) constructs gRenderer
at the end of successful opengl_Setup, before opengl_Init calls opengl_SetDefaults
and its gamma setter. The optional warning at SetDefaults does not by itself
prove a reachable missing-renderer access on this successful path. No blanket
guard or suppression has been added to rendering entry points.

Failure paths do not maintain the same invariant:

- opengl_Close resets gRenderer and clears gpu_state.initted, but the separate
  Renderer_initted flag remains set until rend_Close clears it.
- rend_ReInit closes the old renderer before attempting to initialize a new one.
- rend_SetPreferredState in
  [HardwareBaseGPU.cpp](../../../renderer/HardwareBaseGPU.cpp) ignores that
  reinitialization result, returns success, and calls rend_SetGammaValue when
  gamma also changed. A failed setup leaves the optional empty at that call;
  without a gamma change, the caller still receives a success result despite
  having no active renderer.
- rend_Init marks Renderer_initted before opengl_Init succeeds. Setup failures
  also call opengl_Close, which issues GL calls without first establishing that
  function pointers and a live context exist. Startup and repeated cleanup need
  explicit failure tests before claiming safety.

B04 covers consistent ready-state publication, cleanup of partial resources,
failure propagation to callers, and safe retry. These paths are source-confirmed;
no GL failure was injected and no game was launched in this batch. T03 stays in
Review until the renderer dispositions have runtime evidence. Earlier registry
and WAV candidates were removed by M04 and M02/M03 respectively, as documented
in their validation records.
